## 一、执行摘要

MDOxide 的架构目标清楚：Rope 应作为唯一正文载体，渲染与编辑操作应遵循明确的复杂度上限，大文件应后台加载并按视口处理。当前代码也在保存原子化、恢复身份校验、AST 缓存共享等方面修复了早期问题。

但本轮静态审查确认：**项目仍处于“双正文表示 + 多套状态生命周期并存”的迁移中间态**。主要风险已不只是代码风格，而是以下四类可定位的系统性问题：

1. **正文所有权分裂。** 活动文档同时存在于 `Tab.content: String`、`MDOxideEditor.buffer: Rope` 和撤销快照中，大量代码路径绕过统一文档模型直接修改字符串。
2. **每帧全文档工作。** Raw、Rendered、Split 模式都会在每帧对全文做 blake3 哈希；编辑时还会把整个 Rope 转回 `String`，并克隆完整撤销快照。这直接违反项目自己的每帧复杂度约束。
3. **外部文件同步破坏状态不变量。** 监听器重载没有统一更新原始内容、编码、BOM、编辑器和脏状态；大于 5 MB 且长度不变的外部修改会被 Raw 编辑器静默忽略，后续输入可能覆盖外部内容。
4. **会话持久化存在多套事实源与重复启动 I/O。** `settings.last_open_tabs`、`session.json`、`session.recovery.json`、`recovery/*.json` 和 `autosave/*` 共同描述打开文档；启动时至少存在两条同步恢复路径，后一次会清空并重读前一次恢复的结果。

### 1.1 当前优先级结论

| 优先级 | 数量 | 结论 |
|---|---:|---|
| P0 | 0 | 未发现无需特定条件即可触发的全库级数据破坏或远程代码执行缺陷；这不等于不存在 |
| P1 | 4 | 正文双源与每帧全量工作、外部重载一致性、启动恢复双路径、核心状态聚合体 |
| P2 | 5 | 崩溃快照同步全量写、缓存无字节预算、工作区索引不可取消、代码执行资源边界、不可信工作区自动动作 |
| P3 | 4 | 配置备份语义、恢复文件持久性、PDF 同步解析、分散阈值与错误模型 |

### 1.2 总体判断

当前最优先的工作不是继续增加抽象层或拆分 crate，而是**统一文档所有权，并让所有正文变更经过同一套不变量**。如果这一点不解决，性能优化会继续被同步逻辑抵消，外部修改、自动保存、导出和撤销也会持续依赖各功能自行维护的隐式约定。

## 三、当前核心数据流

```text
文件磁盘
  ├─ 打开/恢复：bytes → 编码检测 → Tab.content: String
  └─ Raw 编辑器首次显示：Tab.content → MDOxideEditor.buffer: Rope
                              ↑                 │
                              │  每帧比较长度/哈希 │
                              └──── 变更时 to_string()

Raw 编辑：
  Rope 输入 → content_dirty → buffer.to_string() → Tab.content
            → 全文 blake3 → diff → EditHistory
            → 全文快照 clone

Rendered 编辑：
  Tab.content &mut String → MarkdownEditor → AST 缓存
                           → 每帧全文哈希 + 全文撤销快照
```

该结构的关键问题不是“有两个性能缓存”，而是**同一正文在不同模式下由不同对象拥有写权限**。Raw 模式以 Rope 为输入源，Rendered 模式直接编辑 `String`，外部文件重载和格式化命令又可直接替换 `String`。这使“当前正文是哪一份”只能依赖调用者自觉同步。

## 四、已确认的设计缺陷

## P1-01 正文所有权分裂，并导致每帧全文档工作量

**证据等级：A（确定）**

### 证据

- `Tab` 保存完整正文 `content: String`：`src/state.rs:1236-1237`。
- MDOxideEditor 另持有 `TextBuffer`/Rope，编辑器实例按 tab 长期保存在 egui 数据中：`src/editor/widget.rs:26-34、551-560`。
- Raw 编辑完成后，整个 Rope 被转换成新 `String` 写回 Tab：`src/editor/widget.rs:839-862`。
- 每次显示编辑器前都调用 `prepare_undo_snapshot_hashed()`：`src/editor/widget.rs:475-480`；Rendered、Split、CSV、Tree 模式也在每帧调用：`src/app/central_panel.rs:1921、1951、2233、2257、2302`。
- 该函数每帧执行全文 blake3；一旦内容与上次快照不同，还会克隆整篇正文：`src/state.rs:2589-2608`。
- Rendered 模式每帧通过 `get_or_parse(self.content)` 计算全文 blake3：`src/markdown/editor.rs:1075-1077`、`src/markdown/cache.rs:123-132`；同一次渲染还会再算一次 `DefaultHasher`：`src/markdown/editor.rs:1242-1251`。
- Raw 模式每帧计算 Mermaid 诊断，而诊断入口再次调用 AST 缓存并哈希全文：`src/app/central_panel.rs:863-870`、`src/markdown/mermaid/validation.rs:125-132`。
- 语义小地图默认开启，每帧遍历全文提取标题并统计行数：`src/config/settings.rs:2646-2648`、`src/app/central_panel.rs:794-810`、`src/editor/outline.rs:662-671`。

项目自己的架构文档要求：

- Rope 是唯一权威正文：`docs/technical/editor/architecture.md:9-42`。
- `to_string()` 只允许出现在保存、导出和整篇复制：同文档 `36-42`。
- 每帧不得执行 `O(N)` 操作：同文档 `44-61`。

当前实现与这三条约束均不一致。

### 影响

1. **每次编辑都复制整篇正文。** 输入一个字符可能触发 `Rope → String` 全文转换、撤销快照全文克隆和多次全文哈希。文件越大，输入延迟越明显。
2. **每帧存在多个全文哈希。** 15 MB 文档在 60 FPS 下，每增加一次全文哈希，理论扫描量约为 900 MB/s；Raw 与诊断、Rendered 与布局身份哈希会叠加。
3. **活动文档至少存在两份正文。** 打开过的每个 tab 都有 `Tab.content`，访问过的较大文档还会长期保留 Rope；编辑期间再加一份撤销快照。
4. **内存预算失真。** 架构文档提出 80 MB 文件约 100–120 MB 内存，而 `ROADMAP.md:34` 记录 15 MB / 36 万行文件峰值 RSS 约 564 MB。该数字来自项目自述而非本报告复测，但已足以说明需要按真实结构重新建立预算。
5. **同步成为正确性的前置条件。** 任何绕过 `MDOxideEditor` 的写入都必须正确同步；遗漏一次就出现显示与保存内容不一致。

### 建议

- 将正文所有权统一到 `Document`/`EditorSession`，Tab 只保留稳定 ID、路径、视图元数据和修订号。
- 为正文引入单调 `revision`，所有缓存使用 `(document_id, revision, config_revision)` 作为身份，而不是每帧重新哈希内容。
- Raw 输入只更新 Rope；Tab 层通过显式快照 API 在保存、导出、搜索时取得不可变视图。
- 撤销记录基于编辑操作或增量 diff，不基于“每帧全文快照”。
- 语义小地图、Mermaid 诊断和 AST 构建改为基于修订号失效，避免每帧全文扫描。

**验收标准：**稳定滚动和仅移动光标时，不产生全文哈希、全文 `String` 转换或全文快照；输入单字符时，新增内存与文档总长度无关。

## P1-02 外部文件重载绕过文档模型，破坏脏状态、编码与大文件编辑器一致性

**证据等级：A（确定）**

### 证据

工作区监听器处理外部修改时：

1. 只用 UTF-8 或有损 UTF-8 解码，忽略 tab 当前编码与 BOM：`src/app/file_ops.rs:1187-1191`。
2. 直接赋值 `tab.content`：`src/app/file_ops.rs:1206-1209`。
3. 仅调用 `notify_external_content_change()`，该函数只增加版本号和 source epoch，不更新 `original_content`、原始哈希、原始字节或编码：`src/state.rs:2572-2579`。

因此，一个未修改文件在外部被改为不同编码或不同内容后重载，Tab 会立刻被视为“有未保存修改”，并继续使用旧的保存编码。

更严重的是大文件 Raw 编辑器的同步判定：

- 编辑器只在“尚无编辑器、长度变化、或小文件哈希变化”时同步：`src/editor/widget.rs:495-560`。
- 对大于 5 MB 且长度相同的文件，代码明确选择“假定未变化”并跳过同步：`src/editor/widget.rs:517-523`。
- 外部重载只改 `tab.content`，不直接通知该编辑器：`src/app/file_ops.rs:1206-1213`。

### 可复现触发路径

1. 在 Raw 模式打开一个大于 5 MB 的 Markdown 文件。
2. 在应用外修改文件，使修改后字节长度不变，例如等长替换一个单词。
3. 监听器重载 `Tab.content`。
4. Raw 编辑器仍显示旧 Rope；因长度相同，继续走 `large_file_skip`。
5. 用户继续输入时，旧 Rope 转成字符串写回 Tab，覆盖刚重载的外部内容；随后保存会把旧内容写回磁盘。

该问题同时说明：即使长度变化触发同步，非 UTF-8 文件也可能被有损 UTF-8 解码，再按旧编码保存，产生字符损坏。

### 影响

- 外部修改可能不可见，随后被静默覆盖。
- 未修改文件在重载后错误显示为“已修改”，触发保存提示、崩溃恢复快照和自动保存。
- 非 UTF-8 文档存在字符损坏风险。
- 编辑器与状态对象不一致时，保存内容取决于最后一次谁写 `Tab.content`。

### 建议

建立唯一的文档变更入口，例如：

```text
replace_from_disk(document_id, bytes, expected_revision)
  → 使用文档既有编码策略解码
  → 更新正文、原始字节、原始哈希、编码/BOM、修订号
  → 使 Raw/Rendered/预览/搜索/导出缓存统一失效
  → 发出单一 ContentReplaced 事件
```

编辑器同步必须依赖 `content_revision`，不能依赖长度或“大文件假定未变化”。外部修改与本地未保存修改冲突时，应提供明确的选择，而不是仅写日志/Toast。

**验收标准：**大文件等长替换、非 UTF-8 外部修改、BOM 变化、连续两次外部修改均能正确反映；干净重载后不显示为脏；无任何旧缓冲覆盖新内容路径。

## P1-03 打开会话存在多套事实源，启动阶段重复同步读取

**证据等级：A（确定）**

### 证据

启动时存在以下流程：

- `main()` 加载一次配置：`src/main.rs:241-253`。
- `AppState::new()` 再次加载配置：`src/state.rs:3627-3629`。
- `AppState::new()` 立即从 `settings.last_open_tabs` 恢复标签，并同步 `std::fs::read` 每个文件：`src/state.rs:3653-3654、3672-3737`，读取点 `3712`。
- 随后 `MDOxideApp::new()` 加载 `session.json`，再调用 `restore_from_session_result()`：`src/app/mod.rs:249-275`。
- 第二次恢复先清空全部标签：`src/state.rs:4870-4871`。
- 再通过 `resolve_tab_content()` 同步读取每个文件：`src/state.rs:5444-5477`，读取点 `5447`。

因此，在“存在有效 session 且无崩溃提示”的常规启动中，同一批文档会被两条恢复路径读取两次；第一次结果被第二次清空。

此外，`restore_from_session_result()` 在清空标签后，如果所有文件都读取失败，会返回 `false`，但不会恢复清空前的标签。结果是本次启动丢失了已经成功恢复的标签集合，只能显示空文档/欢迎页。

### 事实源清单

| 数据 | 位置 | 作用 |
|---|---|---|
| 上次标签元数据 | `settings.last_open_tabs` | 第一条启动恢复路径 |
| 清理退出快照 | `session.json` | 第二条启动恢复路径 |
| 崩溃快照 | `session.recovery.json` | 判断崩溃与恢复提示 |
| 未保存正文 | `recovery/<tab_id>.json` | 逐标签恢复正文 |
| 自动保存正文 | `autosave/*.autosave` | 打开文件后再次询问恢复 |

这些机制分别有其目的，但当前没有单一恢复协调器决定“本次启动只采用哪一份快照、以何优先级合并”。

### 影响

- 启动 I/O 翻倍，且发生在首帧之前，文件越大越明显。
- 配置读取重复。
- 恢复失败时可能丢失本次启动的可用标签集合。
- 多套机制分别处理 tab id 复用和磁盘身份，虽然目前有路径/哈希校验，但任何新增路径都必须复制这些安全规则。
- 难以证明“恢复不会串标签”在所有组合下成立。

### 建议

- 删除 `AppState::new()` 中隐式的 `settings.last_open_tabs` 恢复；只保留一个显式恢复协调器。
- 先完整构建恢复计划，再原子替换当前标签；不要先 `clear()` 后逐个读取。
- 使用稳定文档 ID 与磁盘身份，不依赖每次启动重置的 tab 序号。
- 大文件恢复应复用后台加载路径，至少在首帧后异步解码。
- 恢复失败应保留旧标签或明确显示失败项，不得让局部失败清空整体。

**验收标准：**单次启动每个文档最多读取一次；恢复计划失败不改变现有标签；`session.json`、崩溃快照和 per-tab recovery 的优先级有唯一实现和测试矩阵。

## P1-04 `AppState`/`state.rs` 仍是高耦合状态聚合体

**证据等级：A（确定）**

### 证据

`AppState` 同时拥有：

- 标签、活动索引、下一个 ID；
- 设置与 settings_dirty；
- UI 状态；
- 应用模式、工作区、文件监听器；
- 回链索引、LSP、诊断；
- 恢复冲突。

见 `src/state.rs:3579-3617`。

同一文件还定义：

- 选区与多光标：`190-594`；
- 代码折叠：`644-…`；
- `Tab` 与全部编辑、保存、恢复逻辑：`1225-…`；
- 文件类型、二进制检测、字符坐标转换。

`src/state.rs` 当前为 7,975 行。`docs/technical/app-state.md:108-121` 仍将标签、设置、UI、工作区和监听器描述为一个聚合。

### 影响

- 文档模型、编辑器模型、工作区基础设施和 UI 共享一个可变根，任何新功能都容易直接操作内部字段。
- 纯逻辑（多光标、坐标、折叠）难以独立测试和复用。
- 恢复、保存和 UI 生命周期互相牵连，前面几项一致性问题都与此结构有关。
- 大型 `impl` 拆文件只能改善导航，不改变可变性与依赖方向。

### 建议

按变化原因而非技术层拆分：

- `Document`：正文、路径、编码、原始哈希、修订号。
- `EditorSession`：Rope、光标/选区、撤销、折叠、视口。
- `WorkspaceState`：文件树、索引、监听、工作区设置。
- `UiState`：对话框、面板、提示和交互瞬时状态。
- `SessionCoordinator`：唯一负责启动恢复与周期快照。
- `SettingsStore`：单一加载/合并/持久化入口。

不要求立即拆 crate，也不建议引入通用 service/repository 层。

## 五、P2 级设计风险

## P2-01 崩溃恢复在 UI 线程序列化完整未保存正文，每 5 秒一次

**证据等级：A（确定路径），B（卡顿程度）**

- 周期持久化间隔为 5 秒：`src/config/session.rs:42、1158-1161`。
- 每个 UI 帧检查是否有未保存文档；满足节流条件即执行恢复：`src/app/mod.rs:788-813`。
- 恢复函数遍历所有修改过的标签并同步序列化每篇全文到 JSON：`src/state.rs:4752-4769`、`src/config/session.rs:760-803`。
- JSON 字符串转义会使输出大于原文；写入发生在主线程调用栈内。
- 退出时还会再对全部修改文档执行一遍同步恢复写入：`src/app/mod.rs:2698-2724`。

**为什么是设计问题：**恢复数据应在后台以不可变快照写出，主线程只发布快照请求和接收结果。当前实现把“安全恢复”与“UI 响应性”绑定，文档越大，周期卡顿越明显，也会增加磁盘写入放大。

**建议：**每 N 秒或编辑停顿后生成不可变快照，交给单写线程；限制并发写与临时文件；提供写入失败可见状态；恢复文件采用 fsync + 目录同步的可选耐久模式。

## P2-02 缓存按条目数限制，不按内存预算；任一标签关闭清空全局缓存

**证据等级：A**

- AST 缓存最多 32 条，但每条是完整 `Arc<MarkdownDocument>`，没有字节预算：`src/markdown/cache.rs:54-81、103-132`。
- 缓存身份仅为全文哈希；每次访问仍需先对全文做 blake3。
- 关闭任一 tab 时调用全局 `clear_ast_cache()` 与 `clear_block_height_cache()`：`src/app/mod.rs:928-932`。
- 结果：缓存容量上限没有内存意义；打开 32 个大文档可长期保留大量 AST；关闭一个小标签则让其余所有文档缓存失效并重新解析。

**建议：**缓存按字节/节点数预算、按文档引用计数或弱引用管理；清理由文档关闭精确移除，不做全局清空。

## P2-03 工作区索引线程无法取消，文件树事件可反复触发全量重建

**证据等级：A**

- 每次 `sync()` 需要重建时直接 `thread::spawn`，没有 JoinHandle、取消令牌或线程上限：`src/workspaces/file_index.rs:88-109`。
- `reset()` 只替换接收端并递增 generation，旧线程仍继续遍历目录：`112-137`；线程结束前不会观察新 generation：`209-269`。
- 文件创建/删除会把 `needs_rebuild` 置位，并在下帧启动新一轮索引：`src/app/file_ops.rs:1076-1088、1126-1175`。
- 构建产物、保存大量文件或快速切换工作区时，可能同时存在多条遍历线程；旧结果被丢弃，但磁盘 I/O 和 CPU 已发生。

**建议：**使用 `AtomicBool` 取消令牌与单个 worker，按 generation 丢弃旧结果；对文件事件做 debounce/coalesce；对索引文件数和内存设上限并显示进度。

## P2-04 代码执行缺少输出上限、进程树终止与安全临时文件

**证据等级：A（实现），B（安全影响取决于用户运行内容）**

该功能有明确用户动作和语言白名单，不属于自动执行，但资源边界不足：

- 输出通过 `Vec::extend_from_slice` 无上限累积：`src/markdown/code_execution.rs:584-603`。
- 超时或取消只 `child.kill()` 直接子进程，再无限等待 stdout/stderr reader 线程结束：`src/markdown/code_execution.rs:555-581`。若脚本启动继承管道的子进程，超时后仍可能挂住或留下进程。
- 临时脚本路径仅由纳秒时间戳生成，使用普通 `fs::write`，无 `create_new`/权限控制：`src/markdown/code_execution.rs:373-385、446-449`。

**建议：**限制 stdout/stderr 总量并截断提示；独立进程组/会话，超时终止整组；使用 `tempfile`/`create_new`、0600 权限；对运行不可信文档给出明确信任提示。

## P2-05 不可信工作区可自动恢复并启动终端布局，HTML 导出默认允许活动内容

**证据等级：A（默认行为），B（攻击面）**

### 工作区终端布局

- `terminal_auto_load_layout` 默认 `true`：`src/config/settings.rs:2707`。
- 打开工作区后自动读取工作区根目录的 `terminal_layout.json`：`src/app/file_ops.rs:538-572`。
- 布局可定义任意数量的标签、浮动窗口、shell 类型和工作目录，`load_workspace()` 会直接遍历并创建终端：`src/terminal/mod.rs:1180-1235`。

打开一个不可信仓库可能自动创建大量终端或把 shell 工作目录指向非预期位置。当前没有仓库信任提示、数量上限或布局 schema 大小限制。

### HTML 导出

- 完整导出和片段生成都设置 `render.unsafe_ = true`：`src/export/html.rs:947、1098`。
- 这意味着原始 HTML 不经净化直接进入导出文件。若用户把不可信 Markdown 导出并用浏览器打开，脚本可在浏览器中执行。
- 导出文件使用普通 `std::fs::write`，覆盖失败可能截断旧导出文件：`src/export/html.rs:1103-1117`。

**建议：**把“保留原始 HTML”设为显式选项并给出风险提示；对安全模式净化/转义；导出写到临时文件后原子替换；终端布局只在用户确认信任工作区后加载，并限制叶节点数量与文件大小。

## 六、P3 级问题

### P3-01 配置“备份”不保留备份，且缺少 fsync

`save_config()` 的流程是写 `config.json.bak` 后立即 rename 覆盖 `config.json`：`src/config/persistence.rs:254-301`。成功时所谓备份文件随之消失，崩溃窗口内也没有耐久性保证。命名与实际语义不一致。

**建议：**要么保留上一版配置，要么改名为临时文件；按需增加文件与目录 fsync。

### P3-02 会话、恢复与自动保存的“原子写”只保证重命名，不保证掉电耐久

- 会话写：`src/config/session.rs:550-563`。
- 逐标签恢复写：`src/config/session.rs:791-803`。
- 自动保存写：`src/config/session.rs:1329-1340`。

这些路径均未 `sync_all()`，且临时文件名固定为 `.tmp`。对崩溃恢复，这可能导致临时文件存在但内容未落盘。它不直接破坏用户原文件，但会削弱恢复承诺。

### P3-03 大文件阈值分散，功能行为不一致

- 10 MB 仅用于警告：`src/state.rs:27`。
- 1 MB 决定 Tab 的大文件模式：`src/state.rs:1044`。
- 5 MB 决定 Raw 编辑器“大文件跳过同步”和后台加载：`src/editor/widget.rs:113`、`src/app/file_ops.rs:23`。
- 100,000 字节决定编辑器视图优化：`src/editor/mdoxide/view.rs:26`。
- 10 MB 决定禁用 Raw 语法高亮：`src/app/central_panel.rs:665-669`。

同一个 2 MB 文件可能被视为“大文件”的 Tab，却仍被 Raw 编辑器按小文件逻辑每帧哈希；功能可用性因此取决于调用的是哪一层阈值。

**建议：**定义单一 `DocumentSizePolicy`，由文档模型给出容量等级，所有功能引用同一策略。

### P3-04 PDF 打开和缩放仍在主线程整文件解析

打开 PDF 时同步读取并解析整篇以取得页数：`src/state.rs:4007-4024`。页面渲染缓存命中后不会每帧重读，但首次显示和缩放仍同步读取、解析、渲染：`src/app/central_panel.rs:89-187、3036-3047`。大 PDF 会造成可感知停顿。

**建议：**后台解析元数据，页面渲染放在有取消和内存上限的任务中；限制缓存页数和像素尺寸。

## 八、目标状态模型

```text
DocumentStore
├── Document
│   ├── id / path / encoding / BOM
│   ├── TextBuffer (唯一可变正文)
│   ├── revision
│   └── disk_identity (原始哈希、大小、mtime)
├── EditorSession
│   ├── cursor / selections
│   ├── edit history
│   └── viewport / folds
└── ContentSnapshots
    ├── save/export 按需生成不可变视图
    └── 后台恢复写入读取快照

ApplicationState
├── DocumentStore
├── WorkspaceState
├── UiState
├── SettingsStore
└── SessionCoordinator
```

### 必须成立的不变量

1. 任意时刻只有 `Document` 内的 Rope 能修改当前正文。
2. 任何外部正文变更必须通过 `replace_from_disk`，同时更新原始字节、编码/BOM、哈希与修订号。
3. Raw、Rendered、预览、搜索、导出和恢复使用同一修订语义。
4. 缓存键必须包含文档 ID、正文修订和相关配置修订；不得只按文本哈希或 tab 下标。
5. 每帧工作只与可见区域、选择区和固定上限有关，与文档总长度无关。
6. 一次启动只有一个会话恢复协调器；恢复计划全部成功准备后再替换当前标签。
7. 后台任务必须有取消、结果归属和资源上限；关闭文档或工作区后旧任务不得继续产生可见影响。
8. 外部内容与未保存本地修改冲突时，必须显式选择保留哪一份。

## 九、整改顺序

### 阶段 0：先建立失败测试，不先重构

- 大文件等长外部修改后 Raw 编辑器内容必须更新。
- 干净外部重载后 `is_modified()` 必须为 false，编码与 BOM 保持正确。
- 编辑一帧不得产生全文哈希/全文快照（用可注入计数器验证调用次数）。
- 恢复失败不得清空已有标签；启动时每个文件最多读取一次。
- 崩溃快照写入不得在 UI 线程执行。

**验收：**测试在旧实现上失败，在整改后通过；CI 能执行这些测试。

### 阶段 1：统一正文和修订语义

1. 给文档增加单调 revision。
2. 所有缓存和编辑器同步改为按 revision 失效。
3. 删除每帧撤销哈希与全文快照；撤销记录改为操作级。
4. 保存/导出按需生成快照，停止每输入一字符的全文 `to_string()`。
5. 最后移除长期驻留的第二正文副本。

### 阶段 2：统一所有正文写入路径

把以下路径全部改为文档模型 API：

- 外部文件监听重载；
- 查找替换；
- 格式化命令；
- 渲染块提交；
- 编码切换；
- 会话恢复；
- 自动保存恢复。

**验收：**代码搜索中不再存在绕过文档模型的 `tab.content = ...` 写入。

### 阶段 3：收敛启动与持久化

- 删除重复的 `last_open_tabs` 恢复路径。
- 引入 `SessionCoordinator`，先构建恢复计划再替换标签。
- 会话和恢复快照在后台序列化，使用不可变快照与单写队列。
- 大文件会话恢复使用后台加载占位符。

### 阶段 4：运行时资源边界

- 工作区索引用可取消单 worker，并合并文件事件。
- 代码执行限制输出、终止整个进程组、使用安全临时文件。
- 终端布局和 HTML 活动内容改为显式信任/安全选项。
- PDF 页面渲染移至可取消后台任务并限制缓存。

### 阶段 5：清理与防回归

- 统一大小策略，移除分散阈值。
- 清理不是“未来使用”的死代码豁免。
- 拆分 `state.rs` 的领域模型，优先纯逻辑而非技术分层。
- 建立性能基准和架构不变量测试，防止每帧全量操作重新进入代码。

## 十一、结论

当前没有足够证据把任何问题提升为“无条件 P0”。但以下结论可以确定：

1. **MDOxide 目前不是 Rope 单源架构。** 实际是 `Tab String + Editor Rope + 撤销快照 + AST` 的多副本模型。
2. **每帧复杂度约束未落实。** Raw、Rendered、Split 都存在全文哈希；编辑路径存在全文克隆和全文转换。
3. **外部文件修改路径违反文档状态不变量。** 大文件等长修改可导致编辑器显示旧内容，并在后续输入时覆盖新内容。
4. **启动恢复存在重复路径。** 配置与文件被重复读取，恢复失败还可能清空已经恢复的标签集合。
5. **真正的改进起点应是文档所有权与修订语义，不是先拆 crate 或增加抽象层。**

建议把下一阶段目标定义为：

> **一个文档只有一个可变正文、一个修订号和一个外部变更入口；每帧工作量与文档总长度无关；一次启动只执行一次可恢复的会话规划。**

在这三项完成前，继续增加缓存、异步线程或 UI 功能，只会扩大需要同步和验证的状态组合。
