## 四、缺陷清单

### P0 · 数据丢失（已修复）— 会话恢复身份校验顺序错误

`src/state.rs:5283` `try_apply_recovery()`：

```rust
let is_legacy = recovered.path.is_none() && recovered.original_content_hash.is_none();
if is_legacy {
    return Some(ResolvedContent::Recovered(recovered.content.clone()));  // ← 无条件应用
}
// 路径一致性检查在下面，永远走不到
```

**触发条件**：上一会话遗留一个「无身份」恢复文件（无 path、无内容哈希），本会话恰好复用了同一个 tab_id 且该标签对应磁盘文件 → 无关缓冲区被载入，用户一旦保存就**覆盖原文件**。

这正是上游测试 `test_recovery_identity_original_bleeding_repro_rejected` 里记录的线上事故：`task_50_table_inline_formatting.md` 被 `asdasd` 覆盖。

**更严重的是测试自相矛盾**：同一份输入形态被两个测试赋予相反期望——
- `..._legacy_file_path_backed_session_applied`：要求应用（向后兼容）
- `..._original_bleeding_repro_rejected`：要求拒绝（数据安全）

二者不可能同时通过，说明该路径的语义从未被真正定死。

**修复策略（安全优先）**：无身份恢复只允许还原到**未命名标签**（session path 为 None）；有路径标签一律拒绝并留下恢复文件供人工检查。同步把向后兼容测试改写为拒绝断言，注释说明取舍理由。

**验证**：恢复相关 13 个测试全绿，全量 1599 通过。

### P1 · 保存非原子，存在截断风险（未修）

`src/state.rs:4410`：

```rust
std::fs::write(&path, &encoded_bytes)  // 直接覆盖目标文件
```

磁盘满、进程被杀、断电发生在写入中途 → 用户文件被截断为半截内容，且没有 `.bak`。文本编辑器这是不可接受的。

**修复方案（M1）**：写同目录临时文件 → `sync_all()` → `rename()` 原子替换 → 保留一份 `.bak`（可配置）。预计 30 行以内，含单测（模拟只读目录/磁盘满不可行，至少覆盖正常路径与备份生成）。

### P1 · 撤销粒度失控 + `break_group` 空实现（未修）

- `src/editor/mdoxide/history.rs:491`：`pub fn break_group(&mut self) {}` — **空函数**，但被 `Tab::break_undo_group()`、渲染提交队列等多处调用，注释声称「开启新的撤销组」，实际无任何效果。
- 撤销按「每帧 diff」记录（`history.rs:291` 注释自认：「rapid typing creates one step per dirty frame, not one step per typing session」）。连续输入 100 个字符可能产生数十个撤销步，与 MarkText 的「一次输入会话一步撤销」体验差距明显。

**修复方案（M3 交互对齐阶段）**：按时间/操作类型合并（同一块内 <800ms 的连续输入合并为一组）；`break_group` 要么实现分组边界标记，要么删除并清理调用点，不留误导性 API。

### P2 · AST 缓存每次命中都深拷贝整个文档

`src/markdown/cache.rs:67`：`get()` 返回 `entry.doc.clone()`。大文档（数千节点）每帧克隆一次，缓存反而成了分配放大器。

**修复方案**：返回 `Arc<MarkdownDocument>`，调用方读引用；或在 `&mut self` 上暴露闭包访问。改动局部，收益明确。

### P2 · 25% 的文件带 `allow(dead_code)`，存在未接线功能

- 22 个文件级 `#![allow(dead_code)]`（`state.rs`、`markdown/editor.rs`、`rendered_session.rs` 等核心文件在列）
- 实例：`video_embed` 只有类型定义和 `parse_video_embed_url`，`parser.rs` 从不产出 `VideoEmbed` 节点——功能半成品，对应测试 `document_parses_bare_youtube_url_paragraph` 长期失败（已 `#[ignore]` 标注）
- `rendered_session.rs` 头部写「UI integration continues in follow-up tasks」，但实际已接入 `markdown/editor.rs`（1211/1693 行）——注释已过期，容易误导后续维护

**处置**：M1 裁减时随功能一起删除，并把剩余 `allow(dead_code)` 收紧到「确有规划」的模块，写入审查基线。

### P2 · 巨型文件与函数

`state.rs` 7,969 行（`impl Tab` 单块 1,775 行）、`markdown/editor.rs` 7,091 行、`widgets.rs` 6,446 行；21 个函数参数超过 7 个（最多 10 个）。

**处置**：不主动重构（违反变更纪律），但 M2/M3 新增 UI 代码必须放独立模块，禁止继续往这三个文件里堆。

### P3 · 配置「备份」名不副实

`src/config/persistence.rs:265`：先写 `config.backup.json`，再 `rename` 覆盖正式配置——备份文件随即消失，且无 `sync_all()`。命名误导，崩溃窗口内仍是「旧配置完好、新配置丢失」，不算致命。

### P3 · clippy 基线 261 条

CI 目前无法启用 `-D warnings`。建议 M1 先 `cargo clippy --fix` 清掉自动可修项（约 40%），其余建立豁免清单，逐步收敛。
